在 Ubuntu 24.04 用 Docker 运行 Humble + Gazebo Classic：显卡、挂载、DDS 串台踩坑全记录

# Docker# ROS 2# Gazebo# 踩坑

关键词：ROS 2 Humble、Gazebo Classic、Docker、混合显卡（Intel + NVIDIA）、 FastDDS 共享内存、ROS_DOMAIN_ID、--ipc=host、ros2 daemon

主机 Ubuntu 24.04，比赛要求 Ubuntu 22.04 + ROS 2 Humble + Gazebo Classic 11。 用 Docker 套一层是最省事的方案，但这一路上显卡、设备权限、目录挂载、 共享内存、ROS 2 CLI 各埋了一个坑。这篇把每个坑的现象、排查命令、 根因和修法都记下来，附实测数据。

懒人版结论——如果只想抄三行，就抄这三行：

# 1) 显卡：容器用户要进宿主 render/video 组，并且把设备指到核显--group-add "$(getent group render | cut -d: -f3)" \--group-add "$(getent group video  | cut -d: -f3)" -e DRI_PRIME=pci-0000_00_02_0​# 2) 隔离：给每套仿真一个专属 DDS 域，并在容器内清掉共享内存残留-e ROS_DOMAIN_ID=42bash -lc 'rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps_* /dev/shm/fastdds_*; ...'​# 3) 容器里所有 ros2 CLI 都加 --no-daemon（daemon 会坏）ros2 service list --no-daemon

0. 先交代环境

宿主机 容器
系统 Ubuntu 24.04 (noble) Ubuntu 22.04 (jammy)
内核 7.0.0-34-generic（HWE 内核，包版本 7.0.0-34.34~24.04.1；24.04 默认是 6.8.x） 共用宿主内核
Python 3.12.3 3.10.12
中间件 — ROS 2 Humble
仿真 — Gazebo Classic 11.10.2
Docker 29.1.3（overlayfs / systemd cgroup） —

笔记本是混合显卡：Intel Raptor Lake 核显（00:02.0）+ NVIDIA 独显（01:00.0）， 宿主加载的是 NVIDIA 开放内核模块 595.91.07。 注意：这台机器上 nvidia-smi 本身是坏的（Failed to initialize NVML: Unknown Error）， 桌面一直靠核显在渲染 —— 这一点后面很关键。

比赛环境为什么要 22.04：官方仿真包是按 Humble + Gazebo Classic 11 编的， 而 Gazebo Classic 已经停止维护，24.04 上没有对应版本。套容器是最现实的选择。

容器骨架大致长这样：

docker run --rm -it \  --name ican-sim \  --network host --ipc=host \  --device /dev/dri \  -e DISPLAY="$DISPLAY" -e QT_X11_NO_MITSHM=1 \  -v /tmp/.X11-unix:/tmp/.X11-unix:rw \  -v "$WS_HOST:/home/dev/ws:rw" -w /home/dev/ws \  ican-humble:22.04 bash -lc 'source /opt/ros/humble/setup.bash; exec ros2 launch ...'

--network host 让容器和宿主共用一个 ROS 图（也埋下了后面的串台坑）， --ipc=host 共用共享内存（埋下了幽灵发布者的坑）， --device /dev/dri + X11 socket 是图形界面的通路。

1. 显卡：给了 /dev/dri 还是慢，还刷 failed to load driver: nouveau

现象

容器日志里刷屏：

[gzserver-1] libGL error: glx: failed to create dri3 screen[gzserver-1] libGL error: failed to load driver: nouveau[gzclient-5] libGL error: glx: failed to create dri3 screen[gzclient-5] libGL error: failed to load driver: nouveau

Gazebo 窗口能开，但卡到没法看；有时开一会儿 gzclient 直接没了。

排查

# 1) 宿主机上哪块 GPU 对应哪个 render 节点ls -l /dev/dri/by-path/# pci-0000:00:02.0-render -> ../renderD129     # Intel 核显# pci-0000:01:00.0-render -> ../renderD128     # NVIDIA 独显​# 2) 宿主机用的是哪套驱动lsmod | grep -E '^nvidia|^i915|^nouveau'# nvidia nvidia_drm nvidia_modeset nvidia_uvm i915   ← 闭源/开放模块，没有 nouveau​# 3) 容器里设备权限docker exec ican-sim ls -l /dev/dri/# crw-rw---- 1 root   992 226, 128 renderD128   ← 属组是宿主的 render(992)# crw-rw---- 1 root   992 226, 129 renderD129# crw-rw---- 1 root video  226,   1 card1       ← card* 属 video(44)docker exec ican-sim id# uid=1000(dev) gid=127(dev) groups=127(dev)     ← 不在 992/44 组里

两个问题叠在一起：

  1. 权限：--device /dev/dri 是把宿主设备文件原样映射进容器，属组还是宿主 的 GID（本机 render=992、video=44）。容器里的用户（uid 1000）不在这些组， 打开设备直接 Permission denied。实测直接报： failed to open /dev/dri/renderD129: Permission denied。
  2. 设备选择：renderD128 是独显、编号更小，Mesa 默认就挑它；而容器里 没有 NVIDIA 驱动（镜像里只有 Mesa 的 nouveau_dri.so，宿主用的却是 官方模块，nouveau 根本驱不动），于是加载失败 → 退回 llvmpipe 软件渲染， 所有渲染都压到 CPU 上，又慢又容易崩。

走过的弯路

试过 MESA_LOADER_DRIVER_OVERRIDE=iris（强制 Intel 驱动），结果照样失败：

libGL error: glx: failed to create dri3 screenlibGL error: failed to load driver: iris

因为只换了"驱动名"，没换"设备"—— Mesa 还是去开独显那个 render 节点， iris 当然驱不动 NVIDIA 的卡。驱动名和设备必须一起指定。

修法（实测通过）

docker run --rm -it \  --device /dev/dri \  --group-add "$(getent group render | cut -d: -f3)" \  --group-add "$(getent group video  | cut -d: -f3)" \  -e DRI_PRIME=pci-0000_00_02_0 \  ...
  • --group-add 把宿主的 render/video GID 带进容器的附加组 → 权限通了；
  • DRI_PRIME=pci-0000_00_02_0 把设备指到核显（00:02.0，冒号点号换成下划线）。

验证：容器里 id 变成 groups=127(dev),44(video),992， 同一套真实世界 + X11 的启动方式，GL 驱动报错从刷屏变成 0 条。 （也试过只映射核显节点 --device /dev/dri/renderD129，仍然 failed to load driver: nouveau —— 设备选择不是只看节点编号，所以还是 DRI_PRIME 更可靠。）

另一种"正道"是装 nvidia-container-toolkit 后用 --gpus all 走独显。 这台机器 toolkit 装了、docker 也注册了 nvidia runtime，但宿主 nvidia-smi 报 Failed to initialize NVML: Unknown Error，独显本身不可用，所以这条路 暂时走不通 —— 先确认 nvidia-smi 是好的，再考虑走独显。

这个 NVML 错误通常是驱动版本与正在运行的内核模块不匹配（比如 apt 升级了 用户态驱动但没重启，或 HWE 内核更新后 DKMS 模块没跟上）。排查方向： cat /proc/driver/nvidia/version 对比 dpkg -l | grep nvidia-driver， 重装驱动（sudo apt install --reinstall nvidia-driver-595，或切回 550 稳定版） 后重启。本文场景下核显已够用，就没再折腾独显。

2. CPU 不是"挂载"出来的

常见的误解是"要把 CPU 挂进容器"。其实容器默认就和宿主共享 CPU， 不写 --cpus / --cpuset-cpus 就是用满。真正决定仿真快慢的是单核性能 + 物理引擎的实时率（RTF），而不是核数。

量 RTF 的办法（Gazebo 自带）：

docker exec ican-sim gz stats -d 5# Factor[0.78] SimTime[109.46] RealTime[294.22] Paused[F]# Factor[0.71] ...

实测这套场景 RTF 稳定在 0.70~0.80：仿真时间比真实时间慢 20~30%， gzserver 常驻 200%+ CPU。也就是说"仿真里 1 秒 ≈ 墙上 1.3 秒"， 写超时逻辑时如果混用仿真时间和墙钟时间，就会得到莫名其妙的结果。

想让评测跑得快，最有效的不是加 CPU，而是别开 GUI：gui:=false 时 gzclient 不渲染，同样的任务从"看着卡"变成几十秒跑完。

3. 文件夹挂载：四个真实的坑

3.1 挂载源不存在时，Docker 会悄悄建一个空目录

如果 -v /host/path:/in/container 里的 /host/path 不存在，Docker 不报错， 而是自动创建一个 root 所有的空目录挂进去。容器里看起来一切正常， 只是"工作空间是空的"——排查起来非常费劲。

所以脚本里最好显式检查：

[[ -d "${WS_HOST}" ]] || { echo "找不到工作空间：${WS_HOST}" >&2; exit 1; }

3.2 软链接不会被跟随

项目搬家后想用软链接"让旧路径还能用"，实测：

ln -s /home/cisyam/桌面/ican /tmp/link_testdocker run --rm -v /tmp/link_test:/ws alpine ls /ws# docker: Error response from daemon: error while creating mount source# path '/tmp/link_test': mkdir /tmp/link_test: file exists

Docker 不跟随软链接，挂载源必须是真实路径。所以别指望用软链接兼容旧路径， 要么改脚本里的路径，要么让脚本自己定位。

这个 mkdir ... file exists 报错是老版本 Docker/containerd 在做 mount source 校验时的怪异行为（它试图对源路径 mkdir，撞到已存在的软链接就报 EEXIST； 不同版本表现不完全一致，新版本有的会直接拒绝、有的能跟随）， 不是你 ln -s 写错了——最稳的做法仍然是挂载源直接给真实路径。

3.3 别写死绝对路径，让脚本自己算

早期脚本里写死 WS_HOST=/home/cisyam/ican_shoot，项目一搬到桌面就全线失效， 更糟的是产生了"两份一模一样的拷贝"，改 A 跑 B，看起来就是"改了代码容器里没变"。

改成按脚本自身位置定位，一次解决：

SELF="$(readlink -f "${BASH_SOURCE[0]}")"WS_HOST="$(dirname "$(dirname "${SELF}")")"      # docker/ 的上一级 = 项目根WS_CONT="/home/dev/ican_shoot"docker run ... -v "${WS_HOST}:${WS_CONT}:rw" -w "${WS_CONT}" ...

"单目录架构"：工作区就是提交包本身，容器里编译产物 build/ install/ log/ 直接落在项目里，宿主改代码容器立刻可见，不存在同步问题。

顺带一提：挂载源路径里带中文（/home/cisyam/桌面/ican）完全没问题， 实测正常，不用为此搬家。

3.4 一个项目两套脚本，容器名撞车

多套启动脚本共用 --name ican-sim 时，后启动的会失败或把前面的踢掉。 统一容器名 + 开跑前 docker rm -f 清场，比事后猜要省事。

4. --ipc=host 的共享内存幽灵（本次最狠的坑）

现象

仿真明明起来了，任务却整段垮掉：四发子弹全部 0 分，而且子弹不是打偏， 是从固定点垂直上天；状态机日志里出现 上一状态 11709.2s、-11680.2s 这种鬼数字；一趟本该 30 秒的任务跑了 15 分钟。

排查

# 1) 机器人真值位置 vs shooter 查到的位姿#    真值 (0.015, -0.006)，shooter 算出来 (-1.188, +0.549, +0.102)，枪口还指向世界 z 轴python3 tools/probe_shot.py​# 2) 看 /tf 到底有几个发布者ros2 topic info /tf -v --no-daemon | grep "Node name"# robot_state_publisher# robot_state_publisher     ← 同一个名字出现两次？进程却只有一个！# 3) 按 (父→子) 去重打印整棵 TF 树python3 tools/probe_tf_all.py 5# odom → base_footprint   ←★ 同一对边出现两种取值#   正常值 xyz=(+0.015,-0.006,+0.000) q=(0,0,0,1)#   幽灵值 xyz=(-1.131,+0.707,+0.102) q=(-0.41,+0.58,-0.41,-0.58)

画成图就是这样——同一对父子坐标边，TF buffer 里同时躺着两条互相矛盾的数据。

正常情况是一棵连通的树：

  odom ──► base_footprint ──► base_link                │                ├──► laser_cylinder_link ──► laser_link                ├──► camera_link                └──► wheels...

中招之后，odom → base_footprint 这条边上同时挂着两个值：

  odom ──► base_footprint ──► base_link                │                ├── 正常值 xyz=(+0.015,-0.006, 0)      ◄── 本轮仿真                └── 幽灵值 xyz=(-1.131,+0.707,+0.102)  ◄── /dev/shm 里的 FastDDS 残留段​  shooter 查 TF 时可能命中任意一条；命中幽灵值 → 枪口指向世界 z 轴

根因

--ipc=host 下容器和宿主共用 /dev/shm。上一轮仿真进程被杀后，FastDDS 留在共享内存里的段没有清干净，新起的节点会把这些残留当成"活数据"读进来：

  • /tf 上冒出并不存在的发布者，odom→base_footprint 被陈旧值覆盖；
  • 依赖 TF 求"枪口在世界的位置和朝向"的 shooter 因此算出一个假位姿， 子弹从固定点垂直发射；
  • /clock 跟着跳变，任何用仿真时间的超时/计时全部失真。
$ ls -la /dev/shm | headfastrtps_14785ad6596e5479   ← 12:04 本轮fastrtps_389d0da2a137400c   ← 11:42，那个容器早没了fastrtps_74e2db6d08d1a3df   ← 11:51，同上...

修法：域隔离 + 进容器清共享内存

# 1) 给这套仿真一个专用 DDS 域，幽灵留在默认域 0，看不见了-e ROS_DOMAIN_ID=42​# 2) 启动前清掉共享内存残留。注意：这一步要在**容器内**做#    宿主侧那条 rm 在某些受限 shell 下会静默失败（被沙箱拦掉）docker run ... ican-humble:22.04 bash -lc '  rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps_* /dev/shm/fastdds_* 2>/dev/null  source scripts/setup_env.sh && exec bash scripts/run_sim.sh gui:=false'

改完这个，同样的任务从"四项射击全 0、跑 15 分钟"变成"满分、30 秒"。

经验：只要用了 --ipc=host + DDS，每次启动前清 /dev/shm/fastrtps_*， 并且给每套仿真一个独立 ROS_DOMAIN_ID，能省掉一整类玄学问题。

5. 容器里的 ros2 CLI：daemon 会坏，加 --no-daemon

现象

启动脚本里"等服务就绪"的循环永远等不到，最后打印"服务不存在"放弃 —— 但服务明明在。

$ ros2 service list          # 空！$ ros2 param get /shooter bullet_speedxmlrpc.client.Fault: <Fault 1: "<class 'RuntimeError'>:!rclpy.ok()">

根因

ros2 CLI 默认走一个后台 daemon 做发现，这个 daemon 在容器里很容易进入坏状态 （!rclpy.ok()）。坏掉之后 ros2 service list 不报错、直接返回空， 脚本据此判断"服务没起来"，于是白等 30 秒后放弃 —— 表现就是"仿真起不来/参数没生效"。

修法

ros2nd() { ros2 "$@" --no-daemon; }     # 所有 CLI 调用都绕过 daemonros2nd service list | grep -q '/shooter/shoot'

6. set -o pipefail + grep -q = 假失败

现象

仿真日志里明明白白有 Shooter services ready，脚本却打印"仿真启动失败"。

根因

set -Eeuo pipefaildocker logs ican-sim 2>&1 | grep -q 'Shooter services ready' && echo ok# → 判失败

grep -q 一匹配到就退出并关闭管道，上游 docker logs 收到 SIGPIPE 返回 141， pipefail 会把整条管道的退出码判为失败。日志越大越必现 （我们的日志被 TF 警告刷到两万多行）。

修法：别用管道判内容，捕获后做字符串比对

sim_log_has() { [[ "$(docker logs ican-sim 2>&1 || true)" == *"$1"* ]]; }sim_log_has 'Shooter services ready' || { echo "启动失败"; exit 1; }

8. 最后

回头看，真正花时间的不是"把 22.04 跑起来"（那部分半小时就够），而是 设备权限、共享内存残留、CLI daemon 这类"不报错但行为不对"的坑： 它们不给你明确的错误信息，只让你看到"结果不对"。

如果重来一次，我会在第一天就把这三件事写进启动脚本：

  1. --group-add render/video + DRI_PRIME 指核显；
  2. 每套仿真一个独立 ROS_DOMAIN_ID，启动前清 /dev/shm/fastrtps_*；
  3. 所有 ros2 CLI 加 --no-daemon，所有"判日志"改成字符串比对。

环境：Ubuntu 24.04 宿主 + Ubuntu 22.04/ROS 2 Humble/Gazebo 11 容器， Docker 29.1.3，Intel 核显 + NVIDIA 独显混合笔记本。文中所有修法均为本机实测。
